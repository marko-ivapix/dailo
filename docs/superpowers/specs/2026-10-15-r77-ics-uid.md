# R77 — Calendar events are recognized by their UID (data model)

**Date:** 2026-10-15 · **Status:** point 4 of the outside review ("Ponovni uvoz verovatno pravi duplikate → prepoznavanje već uvezenih događaja po UID-u"), accepted by the user ("Sve se slažem, ali ostavi pod broj 1…"). The source confirmed it: R52 read the UID but compared only title, day and time against open tasks. · **Release:** `2.0.0-alpha.104`.

## The field

`task.icsUid` is the UID of the calendar event a task was made from.

| Value | Meaning |
| --- | --- |
| missing or `null` | not from a calendar file (every task before R77) |
| a string of 1–500 characters without control characters | the event's `UID`; for one changed occurrence of a series, `UID#RECURRENCE-ID` |

- **Helper:** `Core.validIcsUid(value)`.
- **Set only by the import.** The task window does not show or change it.
- **The next occurrence of a repeating task** gets `icsUid: null` when the task had one, because the next occurrence is Dailo's own. Tasks without the field stay without it.
- **Templates** pick their task fields by name and do not keep it. A duplicated task keeps it, so it still counts as the same event.

## The import

- **Parsing:** `parseIcsEvents` keeps `RECURRENCE-ID` as `recurrenceId`, only when an event has one. Events without it are unchanged.
- **`icsImportTasks`** skips an event as "already here" when any of these holds:
  1. **Its UID is on a task**, open or completed, even after the task was renamed or moved. For a changed occurrence, the UID plus its `RECURRENCE-ID` must match.
  2. **It comes from Dailo's own export** (`<task id>-plan@dailo` or `<task id>-due@dailo`) and that task is here.
  3. **The same UID came earlier in the file.**
  4. **It has the same title, day and time** as an open task, or as an earlier event in the file. This is the R52 rule, and it still covers events without a UID and tasks imported before R77.
- **What a draft keeps:** the event's UID, as `icsUid`.
- **Changed occurrences:** two changed occurrences of one series are two tasks.
- **Unchanged:** past and repeating events, the limit of 500, the question before importing, and Undo.

## Storage, backups and sync

- **Core:** `normalizeState` clears a stored invalid `icsUid` to `null` and does not add the field to tasks that lack it. Older tasks stay byte-for-byte the same, so sync has nothing new to send.
- **Backups:** `Backup.validateDomain` refuses a task with an invalid `icsUid` (error `icsUid`). Older backups have no field and validate unchanged. Schema V3, IndexedDB v1 and ZIP `backupVersion: 2` are unchanged.
- **Sync:** the UID rides in the task record, which sync stores whole, like `plannedMonth`. It is not device-local.
- **Older app versions** keep the unknown field: their edits assign onto the task, and their backup validation ignores unknown fields. They do not use it for a re-import.

## Not in this step

- An event that moved in the calendar is not moved here; it counts as already here.
- Following a calendar by link, and reading the phone's calendars, are the larger items for later.
