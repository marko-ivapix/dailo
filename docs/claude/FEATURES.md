## Verification status

The latest record is `docs/superpowers/progress-v1-9.md` (Step 6, 2026-10-07): **330 Node tests, 329 passed, 0 failed, 1 todo** (the release gate waiting for the problem-report address), JavaScript syntax for 63 files plus `tests/support/i18n.js` and `sw.js`, 10/10 static browser contracts, registry 3/3, path adapter 2/2 and a clean `git diff --check`. Every V1.9 iPhone check (install, standalone layout, offline launch, update prompt, persistence, backup reminder, Serbian walkthrough, Serbian Quick Add, favorite star) is **manual-pending**.

The V1.7 release record `docs/superpowers/progress-v1-7.md` reports **251 Node tests passing**, syntax checks for **52 JavaScript files**, AST/static checks for the release's Python test files, browser-path-adapter checks, whole-branch review approval, and clean diff evidence. The final distributable and checksum are recorded in Task 7. `pytest` is not part of the verified command path; direct AST and unittest/static entry points are used. Those are recorded release results; this inventory itself does not re-run or certify them.

Native-browser acceptance was not run for the V1.7 release. Python Playwright suites are available as optional developer/CI harnesses; their presence is not evidence of execution. User-owned-browser manual checks remain necessary for reload/real IndexedDB persistence, file chooser/download/open, delete/Undo timing, restore/reset/snapshot interactions, drag/drop, overlays/Escape/focus traps/return focus, shortcuts while editing, mobile controls/swipes/touch, layout and assistive-technology behavior. No isolated browser or personal Chrome session is launched by this documentation task.

Fonts and icons are vendored since V1.9, so the app shell no longer depends on a CDN. Scheduled templates/reminders only execute when the ready app is open; they are not server jobs, and the service worker does not run them. Settings → Notifications states this limitation. Local snapshots share browser quota and cannot replace an external ZIP backup.

## Deferred or intentionally excluded

Accounts/authentication, backend/cloud sync, push notifications, a language switch or Cyrillic UI, icon subsetting, collaboration/comments/team workspaces, server-delivered notifications, AI planning, integrations, bulk selection/actions, global Search redesign/tag/priority-aware ranking, full hourly Calendar grid or separate event store, elapsed-time tracking, nested/sub-Goals, weighted Goal contributions, and inline image/PDF attachment previews remain outside the implemented prototype. Native mobile clients and production guarantees are not supplied by this static web build.

## Documentation drift to resolve before using older summaries as instructions

1. `AGENTS.md`, `docs/codex/PRODUCT_BRIEF.md`, `V1_3_SCOPE.md`, `TASKS.md` and `ACCEPTANCE.md` describe the V1.3 baseline. Preserve historical semantics, but use `CLAUDE.md` and `CONTINUATION.md` as the current-version entry points and keep V1.4–V1.7 changes explicit.
2. The older brief/scope excludes Habits from Upcoming; current `deriveUpcomingV3` adds the next scheduled Habit within 14 days and milestone projections. Update current product guidance accordingly.
3. The older Calendar brief says no duration/time-block rectangles. Current planned-time/duration blocks are implemented. Week/Month and Day Detail remain; this is not a standalone hourly grid.
4. V1.3 requires Goal dragging, whereas current Calendar UI exposes only Task drag. V1.6's non-draggable Goal direction matches the UI; make the supersession explicit.
5. The V1.6 spec is now labeled as a completed historical design record; its release ledger remains the evidence source for what shipped.
6. README's short export tree shows only Task attachment paths, while current ZIP exports can include Note/Resource-owned files and histories as well. Its initial import/reset description should point to the fuller typed-confirmation/recovery contract rather than omit it.
7. README mentions native Goal UX suite coverage while also declaring browser acceptance pending. Keep test availability distinct from freshly executed browser results.
8. **Python browser scenarios are out of date for the Serbian UI.** The Playwright scripts `tests/ui-*.py` select elements by English text. Their static contracts still pass (`tests/run-browser-regressions.py --dry-run`, 10/10), but a browser run would fail on text selectors until they are updated. They are not part of release verification.
9. **Some English error shapes changed in V1.9** to "Prefix: detail" so the prefix can be translated, e.g. `Backup exceeds ZIP entry limit (2000)` → `Backup exceeds ZIP entry limit: 2000`, `Invalid backup dueDate` → `Invalid backup: dueDate`, `Invalid tasks record` → `Invalid stored record: tasks`, plus the two `AggregateError` summaries. Existing test regexes still match. Older notes that quote the previous wording are historical.
10. **V1.9 implementation differs from its spec in a few recorded places** (ledger Steps 2, 3 and 6): the `<title>` is plain "Dailo" (version in Settings and the brand tooltip); persistence is requested on the first user click, not after the first save; the i18n functions are `tr`/`trn`/`msg`/`trMessage`/`setLanguage` instead of `t`/`plural`/`setLocale`; tests inject English through `tests/support/i18n.js` instead of per-test `t` stubs; weekday/month names are catalog entries, not `Intl`-derived; localization landed in two commits instead of one per surface; the release gate is a `todo` test instead of a failing one while the address is empty. Not flagged as a deviation in the ledger: spec A describes the icon as a geometric "D" mark on the graphite canvas, while `icons/` and `tools/generate-icons.py` use the sidebar `.brand-mark` rings in white on a full-bleed primary-blue square.

The historical specifications and checklists remain unchanged as traceability records. This current handoff resolves the documentation entry-point/version drift but does not declare any manual browser item complete.
